X_eTaL-Coder: Training and validating a specialized coding agent
1. Goals and recommended architecture
The objective is to turn an existing, general-purpose, open-weight coding LLM into a specialized X_eTaL coding agent, capable of writing idiomatic X_eTaL, using the standard libraries, and improving its own code through compiler, linter, test, and debugger feedback.

The important distinction is that we're not simply teaching a model X_eTaL syntax. We're teaching it to participate in the complete X_eTaL software development process.

I recommend treating this as three closely related projects:

X_eTaL-Coder: A new repository for datasets, training configurations, evaluation benchmarks, model adapters, and OpenCode integration.

X_eTaL-fine-tuning: The existing experimental framework for implementing and comparing fine-tuning methods.

X_eTaL-ML: The educational and visualization framework for explaining the training process, adapter mathematics, and experimental results.

The first milestone should be a reproducible experiment demonstrating that a fine-tuned model performs measurably better than its unmodified parent model.

A crucial distinction is that a passing compiler test does not necessarily represent idiomatic X_eTaL.

For example, a compiler test may deliberately exercise an awkward construct, unusual precedence, or a compatibility feature. These examples are valuable for language understanding but should not automatically become preferred coding examples.

This is metadata for the dataset pipeline; actual training records would use the base model's required chat template and tool-call format.

Teach transformations, not just finished programs
For each high-quality X_eTaL example, generate several related tasks.

A single program can yield examples of creating it from a specification, explaining it, extending it, writing tests, repairing a type error, replacing a loop with an array operation, and identifying an appropriate library function.

But avoid automatically treating every synthetic transformation as correct. Run the compiler, relevant tests, and lint checks; review ambiguous stylistic judgments.

The special problem of X_eTaL idioms
The model needs to learn the distinctions between:

Array-oriented operations versus imperative loops.

Functional composition versus unnecessary intermediate state.

Immutable tuples versus mutable bindings.

Built-in language operations versus library functions.

Macros versus runtime functions.

ASCII source syntax versus decorated mathematical rendering.

Public m: macros versus runtime l: library APIs.

Shape-aware operations versus invalid assumptions about broadcasting.

These distinctions are not reliably learned from syntax examples alone.

I would create an idiom catalog containing a canonical example, explanation, equivalent alternatives, anti-patterns, compiler-validity status, and applicable linter rules.

That catalog can serve three purposes simultaneously: supervised training, retrieval documentation, and evaluation criteria.

Example of a training trajectory
User request

Create an X_eTaL function that performs a specified array transformation using the appropriate library.

Agent inspects documentation

Finds the library interface and examples instead of inventing an API.

Agent writes X_eTaL source

Uses the documented interface and idiomatic array expressions.

Compiler returns a diagnostic

For example, a type or shape mismatch with source location and diagnostic code.

Agent repairs the implementation

Uses the diagnostic and relevant source context, then recompiles.

Agent runs lint and tests

Resolves applicable warnings and checks functional behavior.

Agent reports verified results

Summarizes changes, successful tests, and any remaining limitations.

Train on the full sequence, including tool calls and responses, rather than only the final corrected source.

A model trained exclusively on final answers may become good at producing code but still fail at choosing tools, interpreting diagnostics, and recovering from mistakes.

Prevent training on failed reasoning
A failed agent run is valuable evidence, but not necessarily a good imitation target.

Store complete trajectories for analysis, then construct supervised examples from verified successful actions. Failed attempts can be used as negative examples for preference training, with care to distinguish genuine model mistakes from tool failures or ambiguous specifications.

Also capture the minimal correction whenever possible. This helps avoid an agent that rewrites entire files to fix a single compiler warning.

Prevent contamination
The most serious evaluation risk is that the model memorizes examples from the training repositories and appears to have learned general X_eTaL programming.

I would include three types of benchmark:

Known language, unseen problem: Use established syntax and libraries for a novel task.

Unseen library API: Supply new documentation at evaluation time and test whether the agent can use it.

Unseen diagnostic: Introduce an error pattern not represented in training and test whether the agent can interpret the compiler response.

The unseen-library benchmark is particularly valuable. It tests whether the model has learned how to program in X_eTaL using tools, rather than merely memorizing today's library functions.

In this hypothetical example, SFT improves task completion by 22 percentage points, and preference optimization adds another 8 points.

To establish that such improvements are real, run each model on the same tasks with matched tool budgets, context limits, and decoding settings. Use multiple runs where generation is stochastic, paired bootstrap confidence intervals, and per-category failure analysis.

I would also measure latency, total tokens, tool calls, retries, VRAM peak, and successful tasks per GPU-hour. A model that improves correctness by 5% but takes three times as long may not be the best choice for interactive development.

Idiomatic quality needs independent measurement
Compiler success alone is insufficient.

A model could generate valid X_eTaL while writing unnecessarily imperative code, ignoring array primitives, duplicating library functionality, or introducing unnecessary mutable state.

Use three complementary measurements:

Deterministic linter rules for objectively detectable issues.

Structural metrics such as unnecessary loops, complexity, and duplicated expressions.

Blind human review or a carefully calibrated evaluator for style decisions the linter cannot yet express.

Do not let the same model grade its own outputs without independent verification.

9. Improvements I would add to the original concept
There are four important opportunities beyond straightforward fine-tuning.

First, train for library discovery, not library memorization. X_eTaL is evolving. A model that memorizes today's APIs may become obsolete quickly. The agent should be rewarded for inspecting documentation and adapting to unfamiliar interfaces.

Second, treat compiler and linter feedback as structured learning signals. Classify diagnostics by root cause, track repeated failures, and measure whether subsequent model versions eliminate those failure categories. This can eventually feed the ICL/ICRL and offline fine-tuning workflows.

Third, use the language's own compiler to create a self-improving dataset. Generate candidate solutions, validate them, minimize failing examples, and retain verified repairs. Human review remains necessary for style and semantic ambiguity, but much of the mechanical validation can be automated.

Fourth, build an educational experiment explorer in X_eTaL-fine-tuning. It could compare adapters, training loss, held-out success rates, linter violations, and agent trajectories, linking measured outcomes to the LoRA and related mathematics already demonstrated in the project.

2. The model can be smaller because the domain is smaller

One additional possibility: distillation

I agree with your underlying reasoning: X_eTaL is a much smaller domain than Rust, so a smaller specialized coding model may achieve a high level of competence with substantially less training data.

But the goal should not be to make a small model memorize the entire language. It should be to combine:

A capable pretrained reasoning model + compact X_eTaL specialization + authoritative tool access + compiler-verified feedback.

That combination may be more important than the difference between dense and MoE.
